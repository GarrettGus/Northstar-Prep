# Review and migration status

## Implemented

- Removed the previous cloud database/auth SDK, injected configuration, public hub paths and security-rules file.
- Added Neon Postgres with a Vercel API boundary; credentials never enter the browser bundle.
- Added household login, signed seven-day sessions, secure production cookies, database-backed login attempt limits, JSON/origin checks and fail-closed configuration handling.
- Added server-side schemas for inventory, appliances and plans; malformed backups and unsafe image URLs are rejected.
- Atomic state updates use revision checks and bounded conflict retries. Shopping purchases are idempotent and cannot partially add/delete or overwrite an inventory ID collision.
- Restore includes the family plan and retains backup record IDs; merges preserve unrelated existing records.
- Polling results carry revisions so older responses cannot replace newer data. Failed writes keep forms open; delete succeeds before closing an editor.
- Removed hardcoded family identities and legacy recovery IDs before public publication.
- Water units convert to US gallons; bottle/case sizes can be specified. Expired food/water are excluded, and expiration compares local calendar dates through the end of the expiry day.
- Fractional number inputs, prototype-safe grouping, local development API, backup URL cleanup and responsive navigation fixes retained.
- Consumption history records dated usage and notes, derives burn-rate/depletion forecasts only with sufficient history, and round-trips through JSON backups.
- Added an installable app shell, local authenticated-state cache, bounded offline action queue and reconnect sync.
- Added configurable readiness assumptions and settings backup support.
- Added inventory search/status filters, multi-select and atomic bulk deletion.
- Added accessible names, progress semantics, save/sync/offline indicators and a database health endpoint.
- Audited text and icon-only control colors against WCAG AA contrast (4.5:1 for text, 3:1 for non-text UI components) and darkened the failing pairs (muted labels, delete/status text, macro tags, toggle states); added a regression test that pins the audited pairs' contrast ratios.
- Added Node 22 pinning and pull-request CI for tests and production builds.
- Readiness assumptions (household size, calories/water per person, survival/heat/power goals, battery usable capacity and inverter efficiency) are configurable per household, persisted with the state, and shown as plain-language assumptions on the dashboard. Fuel items can be tagged by fuel type, and heat hours are broken down per type.
- Replaced the single shared household password with individual accounts: email + scrypt-hashed password, a household membership table with owner/member roles, shareable one-time invite links (no outbound email needed), owner-only member removal (blocked for the last remaining owner), and an audit log recording who added, edited, deleted, bought, imported, or changed the plan/settings for every mutation. Session cookies now carry only a user ID; role and membership are re-checked from Postgres on every request. A one-time migration step (`HOUSEHOLD_OWNER_EMAIL` + the existing `HOUSEHOLD_PASSWORD`) creates the first owner account from an existing deployment.
- Normalized the household's single JSONB row into per-collection tables (inventory, shopping items, appliances, plan, family members, contacts, settings), each keyed by `household_id` with indexes on household+category lookups. A write now diffs the incoming state against what was last read and only inserts/updates/deletes the rows that actually changed, inside one version-guarded transaction, instead of rewriting the whole household on every edit; concurrent edits to unrelated records no longer contend. The migration script backfills the new tables from the existing JSONB row once (idempotent, safe to re-run) and leaves that row and column in place as a fallback; the GET/POST `/api/hub` contract (`{data, version}`, optimistic-concurrency retries, backup import/export) is unchanged.
- Added scheduled, encrypted household backups: a Vercel Cron job calls `/api/backup` (authorized by a `CRON_SECRET` bearer header Vercel adds automatically), which encrypts the current state with AES-256-GCM (`BACKUP_ENCRYPTION_KEY`) and records it in Postgres with a checksum and item counts, pruning beyond the most recent 30. Household settings shows the last successful backup's time/counts and recent history, including failures with their error. Restoring one is validated end-to-end before anything is applied: the auth tag and checksum must both check out and the decrypted JSON must pass the same schema used for manual imports, or the request fails with a clear error and nothing changes; a valid one reuses the existing non-destructive, record-count preview and by-ID merge already used for manual JSON backups.

- Moved inventory/shopping item images out of the Postgres state document into Vercel Blob object storage. Any base64 image data carried by an add/update/import action (including legacy backups and offline-queued edits) is uploaded server-side before the write, sniffed against its actual file signature and capped at 4 MB (PNG/JPEG/WebP only); the database only ever stores the resulting object storage URL. Images are namespaced by household and item so ownership is enforced structurally. Deleting an item, bulk-deleting, or replacing its image removes the now-orphaned object from storage as a best-effort cleanup after the save commits. A one-off `npm run db:migrate-images` script moves any pre-existing base64 images already in Postgres to object storage.
- Added the remaining inventory-management scope beyond search/filters/multi-select/duplicate detection (already shipped): atomic bulk quantity edits (set an absolute value or adjust by a delta) and bulk category changes for selected items, validated server-side and applied to only the selected IDs in one version-guarded write; optional barcode capture per item (manual text entry, with camera-based scanning via the browser's BarcodeDetector API as progressive enhancement where supported, e.g. not Safari) that also feeds duplicate detection; and recurring supply entries (a configurable replenishment interval in days from purchase date) that surface a "due for restock" banner on the Supply Hub with a one-tap action to queue the due items onto the shopping list.
- Added automated browser-based accessibility regression coverage (Playwright + axe-core) running against the real shared components (`Header`, `InventoryItem`, `AiModal`, the `useDialogFocus` hook), rendered in an isolated harness so it needs no database/login: covers the dialog focus trap (Tab/Shift+Tab wrap between its controls) and Escape-to-close-with-focus-restoration, icon-only/checkbox accessible names, and the header's `aria-live` sync-status announcements (syncing/queued/offline/synced/error). The sweep surfaced two real defects that are now fixed: the sync-status live region never announced the error state in text (only via color/icon, e.g. still read as "3 queued" while `error` was set) — it now announces "Sync error"; and each inventory row nested a checkbox and a buy button inside a single `role="button"` region (axe `nested-interactive`/`no-focusable-content`), which is now split so the edit control wraps only the icon/name and the checkbox and buy button are independent, sibling controls. `npm run test:e2e` runs the suite locally; CI runs it on every PR after installing a matching Chromium build.
- Added production monitoring and sync-health visibility. `/api/health` reports API/database availability and probe latency unauthenticated (usable as an uptime check) and, for a signed-in member, a 24-hour summary of requests, failed saves, server errors, sign-in failures, rate-limited attempts and average/peak database latency, rendered in **Household settings → Service health** next to the existing header indicators for online/offline state, last successful sync and queued changes. Every API response now emits one structured JSON log line with a request correlation ID (taken from the caller's `x-request-id` when well-formed, generated otherwise, always echoed in the response header and sent by the browser on every call), route, method, status, outcome and latency, with a second `request_failure` line carrying the error type — never its message or body — on failures. The same signals aggregate into per-minute Postgres counters keyed only by route/outcome/status/latency: no household contents, item names, user IDs, emails, IPs or request bodies, so the operational history is safe to retain independently of the data it describes. Counters expire after `METRICS_RETENTION_DAYS` (14 by default), pruned by the daily cron that already takes the backup. Repeated failed writes/server errors on one route raise one alert per `ALERT_COOLDOWN_MINUTES`, claimed in the database so concurrent instances send a single notification, POSTed to `ALERT_WEBHOOK_URL` when configured and written as an `alert` log event otherwise; sign-in failures are counted and displayed but never alerted on. Metrics and alerting are best effort and cannot fail a request.

- Added seasonal preparedness reminders and review workflows. A new `reminders` collection (title, category — Water Rotation, Medication, Batteries, Generator Test, Other — a recurrence interval in days, notes, start date) follows the same add/update/delete/backup-merge path as inventory and appliances. A reminder's due date is `lastCompletedDate` (or `startDate`, if it has never been completed) plus its recurrence interval; "Mark Complete" sets `lastCompletedDate` to today, and "Snooze 7 days" sets `snoozedUntil`, which postpones the due date but never brings it earlier. The Dashboard shows a tappable "N overdue maintenance reminders" banner whenever any reminder's effective due date has passed, linking to the Family Hub tab. A fixed, non-editable catalog of four seasonal checklists (winter, summer, severe weather, evacuation — 5 items each) lives in `shared/checklists.js`; a household's progress is tracked as checked rows (id `${season}__${itemId}`) in a new `checklistChecks` collection, added when an item is checked and deleted when unchecked, reusing the same generic collection actions rather than new endpoint logic. Both collections are included in JSON backup export/import and merge by ID like the rest of household state. Every reminder completion or snooze is additionally recorded, server-side, in a dedicated `northstar_reminder_history` table (distinct from the general audit log) by diffing the reminder before/after each write in `/api/hub`; a new `/api/reminder-history` endpoint (mirroring `/api/audit`) lists this history, shown in a "Recent checks" panel so households can verify recurring checks actually happened over time, not just that a field changed.

- Expanded automated coverage from unit tests to the deployment itself: browser tests for the real signed-in app and migration tests against a disposable Postgres database. A test-only adapter (`tests/support/neonOverPostgres.js`) points the serverless Neon driver's fetch function at a local Postgres connection, so `scripts/migrate.js`, `server/db.js` and the `/api` handlers run unmodified — no fork, no stub, nothing in `api/`, `server/` or `scripts/` aware of the tests. Each suite creates a uniquely named throwaway database, applies the real migration and drops it afterwards; `npm run test:e2e:app` also starts the real dev server and drives it with Chromium. CI runs both on pull requests and pushes to `main`, and the workflow can be triggered manually to prove a migration before it is run against production. The new coverage found and fixed three real defects (below).

- Fixed: `scripts/migrate.js` used `stateSchema` without importing it, so the migration threw `ReferenceError` on any database whose relational tables were still empty — that is, on every first-time deployment, and on any upgrade from the pre-relational JSONB row (the backfill it guards). Deployments whose tables already held data skipped that branch, which is why it survived until a migration test ran the script end to end.

- Fixed: `compareAndSave` guarded its row writes with `EXISTS (... version = targetVersion)`, which is true whenever *any* writer has reached that version, not only the transaction that wrote it. Two devices saving from the same version therefore both applied their row writes, and the loser's stale diff silently overwrote the winner's edit while still reporting a conflict to its own caller. The household row now also records a per-save `writer_token` and the guard matches on it, so a save that loses the compare-and-swap applies nothing at all.

- Fixed: `getBackupRecord` returned the auth tag as `auth_tag` while `decryptBackup` reads `authTag`, so every restore of a scheduled backup failed GCM verification with "This backup could not be verified" — the disaster-recovery path was unusable, and the existing unit tests could not see it because they stub the repository on one side of that boundary.

- Made the Family Hub's household members, emergency contacts and meeting points editable (add/edit/delete for the first two, free-text for the latter), reusing the existing `plan` action, audit history, and backup export/import — the schema, validation and storage for all three already existed but had no UI path other than JSON import. Replaced the AI meal-plan and gap-analysis stubs and the "AI icons are not configured" image-generation path with deterministic readiness math (`computeReadinessGaps` in `shared/readiness.js`): the Dashboard now shows the shortfall against each goal (water gallons, calories, fuel hours, power kWh, with power's shortfall correctly inverted through battery/inverter derating) computed from numbers already on the Dashboard, and a shortfall for water, food or power can be queued onto the shopping list as a generic item with one tap. The smart-suggest stubs on the item and appliance forms were removed outright rather than left as dead buttons; the emergency drill remains an AI stub pending a protected backend. Added a printable emergency binder (plan, meeting points, contacts, household members, a readiness/inventory summary, and seasonal checklist progress) rendered entirely from state already held in the browser, reachable from the Family Hub and Household settings, so it works offline and needs no server round trip.

## Verification

`npm test` covers import validation/merge, atomic purchases, collision protection, cookie tampering/expiration/session-secret rotation, cross-origin rejection, unauthenticated API denial, conflict retries, water conversions, local expiration dates, configurable readiness math (household size scaling, zero-need divide-by-zero guards, battery/inverter loss, fuel-type grouping, and legacy state defaulting), password hashing, invitation token validity/expiry/email-matching, owner-generated password reset link validity/expiry/single-use and the self-service password change endpoint (including its own rate limiting and wrong-current-password rejection), owner/member permission enforcement (including last-owner and self-removal protection), audit log recording, image data-URL signature validation and object-storage cleanup, bulk quantity/category updates (including validation rejections), barcode/recurring-days schema validation, recurring-due date math, the audited color-contrast pairs, and the deterministic readiness gap math (shortfall and shopping suggestion per goal, including power's battery/inverter-derated raw-capacity suggestion, and that a fully stocked household reports every goal as met). Reminders and seasonal checklists are additionally covered: schema validation (category/recurrence), generic add/update/delete/backup round-tripping for both new collections, the seasonal checklist catalog's shape (four seasons, unique item IDs), due-date/overdue/snooze math (recurrence from last completion or start date, snoozing never pulling a due date earlier), that `/api/hub` records reminder-history events on completion and snooze but not on an unrelated field edit, and that `/api/reminder-history` enforces membership and authentication. `npm run test:e2e` (Playwright + axe-core, Chromium) covers dialog focus-trapping and Escape/focus-restoration, icon-only/checkbox accessible names, and live-region sync/error announcements against an isolated harness, plus a full axe accessibility sweep of that harness in its default and dialog-open states. `npm test` also covers monitoring: correlation-ID reuse/generation and stability per response, outcome classification (failed writes vs. auth failures vs. rate limiting vs. ordinary client errors), metric recording and structured logging for both served and thrown responses, the assertion that neither logs nor metrics nor alert payloads carry household contents, metrics/alerting failures leaving the served response untouched, alert threshold/cooldown/claim behavior and the exemption of sign-in failures, the daily cron pruning request metrics, and the health endpoint's public-vs-member response shapes including its 503 fail-closed path. `npm run build` compiles the production frontend. Live database and deployment results are reported in the task, not implied by unit tests.

`npm run test:e2e:app` (Playwright + Chromium, serial, against a disposable Postgres database and the real dev server) drives the flows unit tests cannot reach: signing in, rejecting a wrong password and signing out again; adding, editing and deleting a supply with the stored rows and the audit log checked directly in Postgres; client-side duplicate detection; moving a shopping item into inventory with its details intact; taking a scheduled encrypted backup through the cron endpoint, deleting an item, previewing the restore and merging it back, plus a tampered ciphertext being refused with the household left untouched; two signed-in devices converging on each other's edits, both surviving simultaneous adds, and a stale edit form being refused rather than resurrecting an item the other device deleted; and going offline — edits queued in local storage, nothing reaching the server, the cached household still on screen — then reconnecting and watching the queue drain into Postgres where a third device can see it. It also covers the Family Hub: adding, saving and removing household members, emergency contacts and meeting points, with each checked directly in Postgres (not just on screen) and confirmed to survive a reload; canceling an edit discarding unsaved changes; the printable emergency binder opening with the saved plan and closing again; and the Dashboard's deterministic shortfall offering a one-tap add that lands the right item on the shopping list. `npm test` additionally runs the migration suite against a disposable database when one is reachable (skipped otherwise, always run in CI): the schema applies to an empty database and matches every column, alias and type `server/db.js` reads and writes; re-running is idempotent and preserves existing rows, the owner account and the household version; a pre-relational JSONB row backfills into the relational tables (including collections that blob predates) and is not backfilled a second time over newer edits; a stale save and two concurrent saves each apply exactly once; and an encrypted backup round-trips through the `bytea` columns and decrypts.

Live deployment results are still reported in the task; the suites above exercise a local Postgres, not the production database. Camera-based barcode scanning cannot be exercised headlessly (it needs a real camera and a browser that implements `BarcodeDetector`); the manual barcode text field is the tested, universally-available fallback.

## Remaining limitations

- An owner can generate a single-use, expiring password reset link for a member, and any signed-in member can change their own password. A locked-out *sole* owner (no other owner to generate them a link) still needs direct database access — see [Rollback and recovery](README.md#rollback-and-recovery). No email verification on invite acceptance beyond matching the invited address, and no outbound email at all yet (reset and invite links are both delivered by hand).
- No automatic migration from the old database. Import a JSON export and verify counts and household details.
- Meal planning and gap analysis no longer need AI — they were replaced with deterministic readiness math. The emergency drill still does, and remains explicitly unavailable until a protected backend is added.
- Simplified calorie/power assumptions; no inverter loss, battery derating, surge or individualized nutrition model.
- Offline edits are cached in browser storage and limited to 100 queued actions; clearing site data loses unsynced edits. Keep a downloaded backup for outages.
- Power estimates account for battery usable capacity and inverter efficiency, but not surge loads or individualized nutrition models.
- The browser-based accessibility regression suite exercises `Header`, `InventoryItem`, `AiModal` and the shared dialog focus-trap hook in isolation, and no full color-contrast scan runs automatically (contrast stays covered by the static ratio test). The full-app browser suite covers login, supplies, shopping, backup restore, multi-device, offline flows, and the Family Hub (members, contacts, meeting points, the shelter spot, the printable binder and the deterministic readiness shortfall), but not the appliance manager, reminders/checklists, member invitations or barcode scanning, and it runs on Chromium only.
- The database-backed suites need a Postgres server they can create and drop databases on. They talk to it through a test-only adapter that stands in for Neon's SQL-over-HTTP endpoint, so they verify this application's SQL against real Postgres but not Neon-specific behavior (connection pooling, branch limits, cold starts) or the Vercel function runtime. The full-app suite runs serially against one household, and image upload paths still need `BLOB_READ_WRITE_TOKEN`, so item images are not exercised end to end.
- Login-limit rows should be periodically purged after expiration for long-lived deployments. They store hashed IP identifiers, not raw IP addresses.
- Every mutation is recorded in the audit log, but conflicting edits to the same field still follow successful server processing order rather than a field-level merge.
- Request metrics and alert state live in the same Postgres database they monitor, so a full database outage is visible only in the platform's structured logs (which still receive every request and failure line) and through `/api/health` returning 503 — no counters are recorded and no webhook alert fires while Postgres is unreachable. Alert delivery is fire-once per cooldown and is not retried if the webhook itself fails; the alert is always logged regardless. Each request adds one aggregate upsert to Postgres (a single statement, after the response is composed), which is cheap but not free on a polling client. Metrics are aggregated per minute with no percentile breakdown, and browser-side errors are logged to the browser console only, not collected centrally.
- Automatic backups are also copied off-site to object storage (see [Backups and migration](README.md#backups-and-migration)), so a full Postgres loss no longer takes every recoverable copy with it, but the off-site copy still depends on `BLOB_READ_WRITE_TOKEN` being configured and reuses the same `BACKUP_ENCRYPTION_KEY` — there is no encryption key rotation or re-encryption of existing backups (on-site or off-site) if that key changes; older backups become unrestorable either way and should be treated as invalidated. Backup history is not itself covered by the audit log.
